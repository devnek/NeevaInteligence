Function Highlights

get_reports_metadata()

Purpose: Utility function that acts as a file-based data provider. It scans the reports/ directory for markdown files and parses their headers and initial paragraphs to provide a list of report summaries without loading full content.

home(request)

Purpose: Main landing page controller.

  • GET: Prepares the ContactForm and fetches the top 2 featured reports for the index template.
  • POST: Processes the contact inquiry, persists it to the database, and provides feedback to the user.

reports_list(request)

Purpose: Catalog view. It retrieves metadata for all available research reports and displays them in a searchable/browsable list.

report_detail(request, slug)

Purpose: Content renderer. It maps the URL slug to a specific markdown file, validates its existence, converts the raw markdown content to structured HTML, and renders the full report.

leadership(request)

Purpose: Static content delivery. Renders the professional profile and leadership team information page.

Python Scripts Overview

manage.py

Role: Project Entry Point. The command-line utility for administrative tasks. It allows running the development server (runserver), creating database migrations (makemigrations), applying them (migrate), and creating superusers.

core/forms.py

Role: Data Validation. Defines ContactForm, which maps the ContactMessage model to an HTML form. It handles input cleaning and ensures that only valid data (e.g., proper email formats) is saved to the database.

portal_config/settings.py

Role: System Configuration. The "brain" of the project. It defines database connections, installed apps (including core), security keys, and static file handling via whitenoise for production-ready CSS/JS delivery.

portal_config/urls.py & core/urls.py

Role: Traffic Routing. The project URL configuration includes the app-specific URLs. This separation allows the core app to be modular and reusable in other Django projects.

portal_config/wsgi.py & asgi.py

Role: Server Interface. Standard interfaces for web servers (like Gunicorn or Daphne) to communicate with the Django application. WSGI is for synchronous requests, while ASGI supports asynchronous features.

MVC/MVT Architecture Segregation

This application follows the Django MVT (Model-View-Template) pattern, which is a variation of the classic MVC (Model-View-Controller) architecture.

Model (Data Layer)

Files: core/models.py, reports/*.md
Responsibility: Manages the data and business rules. In this portal, the "Model" is split between the SQL database (for user messages) and the file system (for research content).

View / Template (Presentation Layer)

Files: core/templates/core/*.html, core/static/
Responsibility: What the user sees. Django calls this the Template layer. It handles the layout (base.html), styling (CSS), and interactive components (JavaScript).

Controller / View Logic (Process Layer)

Files: core/views.py, core/urls.py
Responsibility: The glue between the Model and the View. Django calls this the View layer. It receives HTTP requests, fetches data from the Model, and passes it to the Template for rendering.

Data Models

Model Description Fields
ContactMessage Stores lead generation and inquiry data from the contact form. name, email, subject, message, created_at
File System (Reports) While not a DB model, the .md files in reports/ act as the primary content storage. Title (H1), Summary (First Paragraph), Content (Body)
